# dtwatch Audit — Size, Memory, Response Time, and Overall Performance Efficiency

*Prepared 2026-10-02. Scope: full-stack — Django/DRF backend, React/Vite frontend, Docker Compose infrastructure — against the live local dev stack (Docker was reachable this time, so image sizes and `nproc`-based gunicorn math below are measured, not estimated).*

## Where things actually stand

This is the second audit of this codebase (the first, 2026-09-13, covered size/memory/backend/frontend and found the app already past a first perf pass — code-splitting, row-limiting, map-marker memory fixes, all dated and commented in-line). Three weeks of real feature work have landed since then: multi-role RBAC, System Health, in-app Documentation, and a unified Audit Log. None of that work introduced anything alarming — the worst finding below (unprefetched relations on `RfOptimizationReportViewSet`) predates this audit, and the new Audit Log's own in-memory merge (`core/audit.py`) is a known, deliberately-scoped tradeoff bounded by its own 30-day retention job, not a new unbounded-growth risk.

The single biggest theme this time: **almost nothing in this app is paginated, cached, or resource-limited by default — not because anyone got it wrong, but because `settings.py` never set a `DEFAULT_PAGINATION_CLASS`, nothing ever wired Redis into the reporting endpoints, and `docker-compose.yml` has never had a `mem_limit` on anything.** At today's scale (≈4,966 sites, 50,592 sectors) every one of these is cheap. None of them are cheap forever, and two tables in particular — drive-test sessions and imported RF reports — have no natural ceiling at all.

## Backend: queries, memory, and request-path cost

**No `DEFAULT_PAGINATION_CLASS` exists anywhere in `REST_FRAMEWORK` (`backend-django/dtwatch/settings.py:361-381`).** Only three view classes opt into pagination on their own (`SitePagination`, `AuditLogPagination`, `AuthEventLogPagination`) — everything else is fully unbounded by default: `IssueViewSet`, `RfOptimizationReportViewSet`, `DriveTestSessionViewSet`, `OptimizationActivityViewSet`, `UserViewSet`, `MenuPermissionViewSet`, `MenuItemViewSet`, `RoleViewSet`, `ApiKeyViewSet`, `TelemetryIngestKeyViewSet`. Most of these sit on small, admin-managed tables (users, roles, menu items) where this is harmless today. Two don't: `dt-sessions/` and `rf-reports/` are both append-only and grow for as long as the O&M team keeps doing drive tests and importing vendor reports — years, with no archival path.

That gap compounds with a real N+1 problem on exactly one of those two: `RfOptimizationReportSerializer` (`core/serializers.py:1489-1521`) issues an unprefetched query per report for `imported_by`, `kpi_summaries`, `cell_kpis`, and worst, `activities` — and then, **inside that per-report loop**, another query per linked activity for `session_links.count()`. A list call on `rf-reports/` today (dozens-to-low-hundreds of rows, imports are batched) issues four to six times the queries it needs; it will scale linearly worse every year. The same unprefetched-per-row pattern shows up twice more, each lower-stakes: `DriveTestSessionListSerializer.get_uploaded_by_name` (no `select_related('uploaded_by')` on an otherwise-unpaginated session list) and `UserSerializer.get_roles` (no `prefetch_related('roles')`, but NTC's own user count is small enough this barely registers).

**`Sector` has no index on exactly the columns a drive-test upload filters it by.** `core/dt_serving_cell.py:64-70` matches incoming samples to sectors by `pci`, `bcch`/`bsic`, and `scrambling_code` — none of which carry `db_index=True` on a 50,592-row table (only `site` does). Every DT upload — the documented real case is a 363,082-sample, 25-file session — runs this match multiple times per chunked batch, and because national PCI/BCCH reuse means a single physical-cell ID can realistically collide with hundreds of same-ID sectors nationwide, `_match_for_key` (`core/dt_serving_cell.py:82-107`) ends up haversine-scoring a sequential-scan-sized candidate set for every distinct serving cell in the batch. This runs at upload time, not on a user-facing read, which softens the impact, but it's real CPU spent on an unindexed full-table-style scan of the one table in this app most likely to be queried by exactly those columns.

**Nothing is cached.** The only two `cache.get`/`cache.set` call sites in the entire backend are the login-lockout counter and the telemetry ingest rate limiter. SLA, NTA, Monthly Report, and Scatter (`core/reports.py`) each run a full `Site.objects.all()` scan and Python-side aggregation from scratch on every request — `build_monthly_report()` alone does five to ten full passes over the site table per call (a ranking sort, two NTA-threshold passes, a per-region breakdown). The dashboard is worse in a different way: `_stat_value()` (`core/dashboard.py:115-130`) issues seven separate `.count()` queries, some filtered on non-indexed `status`/`deployment_status` columns, on every single login/home-page visit, for a set of numbers that changes rarely. At 5,000 sites this is all sub-second — it's pure repeated work sitting on top of a Redis instance that's already running and already proven in this codebase for exactly this purpose, just never pointed at these endpoints.

What's already solid and doesn't need touching: `Site.region`/`district`, `DriveTestSample.session`, and the Telemetry/Audit Log tables are all correctly indexed; the three `PointField(spatial_index=True)` geography columns get real GiST indexes (confirmed via `0035_postgis_location_fields.py`); `CONN_MAX_AGE=60` with health checks is configured; and the telemetry stats/coverage endpoints are the one area of this codebase that's clearly already had a dedicated perf pass — `.iterator(chunk_size=5000)`, a hard `_MAX_RAW_SCAN`, and 15,000-point stride-subsampling are all in place there.

## Frontend: bundle weight and render cost

A fresh build no longer trips Vite's 500KB chunk warning, but the real eager-load number is bigger than any single chunk suggests. Four pieces load on **every** visit regardless of which page a user lands on: the 291KB main `index.js`, a 53KB `queries.js` chunk (the *entire* `src/api/queries.ts` — every hook in the app, 1,300+ lines, as one shared module), the 42KB react-router chunk, and — the real surprise — a **152KB/45KB-gzip `useMapInvalidateOnResize` chunk**, eagerly pulled in because `SitesPage` (one of three routes deliberately kept non-lazy) statically imports `MapView`, which drags in Leaflet, `leaflet.markercluster`, and every shared map-component dependency as one bundle. Combined with CSS, that's roughly **625KB minified / 185KB gzip before any route-specific code even runs** — every user pays the full map-library cost on first load, including the ones who never open a map.

The map itself has a real scale issue once it's loaded: `MapView.tsx:255-383` builds all ~4,700 site markers in a loop and adds each one individually via `cluster.addLayer(marker)` rather than Leaflet's bulk `addLayers()` — the exact pattern `leaflet.markercluster`'s batch API exists to avoid, since each incremental `addLayer()` call re-triggers spatial-index insertion and re-clustering. This re-runs in full every time the filtered site array changes identity (any filter interaction on the Sites page). `DtCoverageMap.tsx:204` has the identical per-marker pattern for drive-test sample dots. The virtual-scroll sidebar, by contrast, is genuinely virtualized — `@tanstack/react-virtual` capping the DOM to ~30px rows with 12-row overscan, not a cosmetic wrapper around a long list.

`TrpAnalysisPage` is still the single largest chunk (303KB/100KB gzip), correctly lazy-loaded so only users who open it pay for it — the weight is almost entirely `import * as XLSX from 'xlsx'`, a full namespace import of SheetJS for what's likely a single export/import feature on that one page. Five packages in `package.json` `dependencies` — `@radix-ui/react-dialog`, `@radix-ui/react-slot`, `class-variance-authority`, `tailwind-merge`, `lucide-react` — exist solely to support the explicitly-labeled, not-yet-decided `StyleTestPage` trial route; `framer-motion` has zero imports anywhere in `src/` and appears entirely vestigial already. None of these affect the production bundle (tree-shaking handles the unused ones), but they're real install-size/dependency-surface weight worth pruning once the style trial is resolved one way or the other.

React Query's global defaults (`staleTime: 30s`, `refetchOnWindowFocus: false`, a dedicated shorter `gcTime` for DT sessions) are still sensibly tuned from the 2026-08-05 pass. Six hooks poll on intervals between 10-30s (`useLiveSiteSources`, `useTelemetryStats`, `useSystemHealth`, `useTelemetryLiveSamples`, `useTelemetryDtSessions`, `useTelemetryDtSessionSamples`) — each pauses when its tab is backgrounded (React Query's default), so this only compounds for a user with several live-data pages open in separate tabs at once, not a single-page concern. No component in the codebase uses `React.memo` — currently harmless because the one place it would matter (`MapView`) is already protected by a correctly-memoized `filteredSites` prop on the caller's side, but there's no safety net if that changes. `DtExploreTab.tsx` has a nine-deep chain of dependent `useMemo`s/`useEffect`s that's individually correct but structurally fragile — worth a look if that page ever feels janky, not a bug today.

## Infrastructure: images, resources, and startup cost

**No service in `docker-compose.yml` has a memory or CPU limit** — all 8 containers (`db`, `redis`, `django`, `frontend`, and the four maintenance-loop services) run fully unbounded, the same gap flagged three weeks ago and still open. This matters more now than it did then: there are four always-on maintenance containers sharing the `django` image today (`site-sync`, `telemetry-maintenance`, `telemetry-bin-roller`, and the newly-added `audit-log-maintenance`), each holding its own Postgres connection against the same `max_connections=200` ceiling gunicorn's own worker math was sized against — the in-code comment claiming gunicorn's worker cap "keeps connections under ~15" doesn't account for these four siblings. Nothing is exhausted today, but the headroom math is now incomplete in a way it wasn't before this session's work added a third maintenance loop.

The backend Docker image is **1.14GB**, against the frontend's **76.4MB** — roughly 15x larger for what is, at runtime, a much smaller artifact than a built React bundle. `docker history` points to one cause: `backend-django/Dockerfile:12-14`'s single `apt-get install libpq-dev gcc binutils libproj-dev gdal-bin` layer measures **562MB**, about half the final image, and unlike the frontend's explicit two-stage build, the backend Dockerfile has no build/runtime split — the compiler toolchain and `-dev` headers stay in the final image permanently. Since `psycopg2-binary` ships precompiled wheels, `gcc`/`binutils`/`libpq-dev`'s dev headers are plausibly dead weight that only a from-source compile would ever need.

Postgres gets exactly two tuning flags (`max_connections=200`, `shared_buffers=256MB`) and nothing else — `work_mem`, `effective_cache_size`, and `statement_timeout` are all stock defaults despite this being a PostGIS geo-query workload with no query-runaway ceiling at all. On the serving side, the asymmetry between the two static-asset paths is real: the SPA bundle gets gzip and long-lived caching from nginx (`frontend-react/nginx.conf`), while Django's own `/static/`/`/media/` paths are served via `django.views.static.serve` with a comment in the code itself admitting "dev-quality serving (single-threaded, no caching headers)" — no whitenoise, no `STATICFILES_STORAGE` override, nothing compressed. Admin is low-traffic enough that this is a minor finding, not urgent.

Smallest but easiest to fix: `entrypoint.sh`'s `migrate --noinput` and `collectstatic --noinput` run on **every** container start, and because four other services share the `django` image, every `docker compose up` runs both of those five separate times against the same Postgres instance, all racing the same `depends_on: service_healthy` gate simultaneously. Harmless in isolation, pure duplicated I/O at scale.

## What's clean

Worth stating plainly so it doesn't get lost in the findings above: gunicorn's worker/thread formula is CPU-aware and reasonable (12 workers × 4 threads on this host); PostGIS spatial indexes exist exactly where proximity queries need them; the telemetry pipeline's chunking/sampling/stride-subsampling is genuinely well-engineered; the virtual-scroll sidebar is real virtualization, not a wrapper; code-splitting is used consistently across every admin page added this session; logging levels are sane (`WARNING` root, no stray `print()` anywhere in `core/`); and connection pooling, idempotent migrations, and CSV/export streaming are all already handled correctly where they appear.

## Prioritized action list

Roughly ordered by impact-at-current-scale vs. effort to fix — not a commitment to do all of this, just a ranked starting point.

1. **Add `DEFAULT_PAGINATION_CLASS` to `REST_FRAMEWORK`** (settings.py) — one-line config change, immediately bounds every currently-unpaginated endpoint. Lowest effort, affects the most endpoints.
2. **Fix `RfOptimizationReportSerializer`'s unprefetched relations** (`imported_by`, `kpi_summaries`, `cell_kpis`, `activities`, plus the nested `session_links.count()` loop) — a `select_related`/`prefetch_related` change in `RfOptimizationReportViewSet.queryset`, no schema change.
3. **Index `Sector.pci`/`bcch`/`bsic`/`scrambling_code`** — a straightforward migration, directly speeds up every DT upload's serving-cell attribution against the 50,592-row table.
4. **Cache the SLA/NTA/Monthly/Scatter/Dashboard-stats endpoints** with a short TTL (Redis is already running, already used elsewhere) — eliminates the majority of redundant full-table scans on the app's most-visited pages.
5. **Add `mem_limit`/`deploy.resources.limits` to every `docker-compose.yml` service**, especially `django` and `db` — cheap insurance, now more relevant with four maintenance-loop siblings sharing the connection pool.
6. **Switch `MapView.tsx`/`DtCoverageMap.tsx` to bulk `cluster.addLayers()`** instead of per-marker `addLayer()` in a loop — a contained change in two files, fixes the main map re-render cost at 4,700+ sites.
7. **Split the eager map-library chunk out of the critical path** — either lazy-load `MapView` on `SitesPage` or accept the tradeoff explicitly; either way, 45KB gzip on every single page load (including non-map pages) is worth a deliberate decision rather than an accidental one.
8. **Slim the backend Docker image** — drop `gcc`/`binutils`/`libpq-dev`'s dev headers if nothing actually compiles from source, or move to a real multi-stage build matching the frontend's own pattern. Saves image size/pull time, not runtime performance.
9. Smaller/lower-urgency: a Postgres `statement_timeout`, whitenoise (or equivalent) for Django's own static/media serving, pruning the five style-trial-only frontend dependencies once that trial is resolved, and collapsing the 5x redundant `migrate`/`collectstatic` startup calls to run once per `docker compose up` instead of once per service sharing the image.
