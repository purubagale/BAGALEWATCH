# DT-WATCH audit: speed, size, memory and security (web and mobile)

*2026-10-23. Measured on the local stack (dtwatch `d8386d6`, mobile `bfd274d`, release APK of 19 October) unless marked otherwise. Production runs different hardware and data volumes, so the timings show proportions, not prod's exact numbers. Follows the audits of 2026-09-13 and 2026-10-02.*

## In short

Nothing found is an emergency, but five items deserve action before the next prod deploy:

1. **Pillow 12.3.0 has 35 known vulnerabilities** (fixed in 13.0). Pillow decodes the site photos phones upload, so it parses untrusted pictures. DRF 3.17.2 has 3 more (fixed in 3.18.2).
2. **The drive-test session list can take 26 s** when the database cache is cold (0.7 s warm). Counting each session's readings reads about 250 MB of table pages. This is the "Session History is slow" complaint.
3. **Session History's coverage map thinned a long drive by keeping every Nth reading** (cap 15,000 SVG dots; the first version of this audit wrongly said there was no cap). On a 140,000-reading drive that dropped nine readings in ten, and with them more than half of the weak spots: of 2,840 small squares holding a reading under -110 dBm, the map showed 1,298.
4. **Rescue enrolment still trusts the shared app key.** Anyone who pulls that key out of the APK can enrol any number as a rescue beacon from their own phone. Signed registration replaced it for everything else; this one path was never retired.
5. **The phone's offline queue re-reads its whole file on every new reading.** During a drive (a fix every 2 s, up to 5,000 queued readings, 2-3 MB) this wastes CPU and battery whenever uploads fall behind.

- **The session list count.** `sample_count_expr()` counts readings per session with `Count('id')`. The plan shows a bitmap heap scan visiting 31,800 table pages for 24 sessions (918,000 readings, a 405 MB table) instead of counting from the index. Warm that is 0.5 s; cold it is disk reads. Fix: keep a stored `sample_count` on `DriveTestSession`, updated by upload, append, delete and retention (one migration and a backfill), or at least count `session_id` so an index-only scan is possible.
- **Postgres JIT is on.** Every query whose cost estimate is high (this one, about 1 million) gets compiled first, which adds 50-200 ms. `jit = off` is the usual choice for this kind of workload.
- **No `statement_timeout`.** One runaway query (a wide Explore search, an export) can hold a connection and a worker indefinitely. 30-60 s for web requests is a reasonable ceiling; the maintenance jobs can set their own.
- **One drive-test session is sent whole** (every reading, 5.5 MB). The page needs this for the table and route, but the map does not (see the browser section).
- Still open from 2026-10-02: no `DEFAULT_PAGINATION_CLASS`. The big lists are capped in code (500 rows), so this is now low priority.

### Memory

- Django container: **555 MB of its 1 GB limit while idle.** The maintenance runner holds 245 MB (all nine jobs in one process, AI drafts included), and each of the four web workers about 138 MB.
- Peak per request: the site list 40 MB, one large session 62 MB. Four workers of four threads means up to 16 requests at once, so several people opening big sessions together can reach the limit; the worker is then killed and the user sees an error (as happened with the engineering-parameter import on 13 October). Options: two threads per worker, or 1.5 GB for Django on prod (prod has 19 GB).
- Database: 489 MB, of which drive-test readings are 405 MB (139 MB of it indexes). `shared_buffers` 256 MB, `work_mem` 4 MB. That's fine at this size; prod's separate Postgres machine needs its own numbers.
- `DATA_UPLOAD_MAX_MEMORY_SIZE` is 700 MB: a JSON request body of that size is held in memory. nginx stops anything over 25 MB except backup, RF report and attachment uploads (700 MB, admin only). An admin uploading a large RF report as JSON could therefore exhaust the 1 GB container.

### Size

- Backend image 814 MB (was 1.14 GB on 2026-10-02); frontend image 77 MB.

### Security

**Good, verified:**
- Every API route needs a signed-in user unless it is meant to be open. The open ones: sign-in, password reset, SSO, health checks, phone registration, and the phone upload endpoints. Each phone upload endpoint checks the app key itself and is rate-limited (registration 10 a minute per address, speed test sized and rate-capped).
- 23 phone and partner endpoints use signed requests or partner API keys.
- JWT: 15 min access, 12 h refresh, rotated and blacklisted after use.
- HTTPS settings (secure cookies, HSTS a year, proxy header trusted only when `HTTPS_ENABLED=1`) switch on together. The local `.env` keeps them off, which is right for local.
- Django admin is closed, the API schema needs a sign-in, `/media/` is limited to branding and menu icons.
- Rate limits: 1,200/min per user, 120/min per address before sign-in, 30/min on sign-in at nginx.
- Production web packages: `npm audit` 0.

**To fix:**
- **Pillow 12.3.0 to 13.0, DRF 3.17.2 to 3.18.2** (38 known vulnerabilities in total). Pillow is the urgent one, because phones upload pictures it decodes.
- **Rescue enrolment** (`/api/telemetry/v1/rescue-enroll/`) accepts any number with only the shared key. Either require the signed device (the registration flow already proves the number by SMS) or return 410 once the new app is out, as planned on 2026-10-04.
- **The shared app key is still accepted for uploads** (`TELEMETRY_SHARED_KEY_ACCEPTED_UNTIL` is unset). Anyone with the APK can send fake readings under any device id. Signed uploads exist for registered phones; setting a cut-off date is the user's decision, because it stops unregistered phones from sharing.
- **Password-reset links use the request's Host header.** That's safe only if prod's `ALLOWED_HOSTS` names the real host; the local `.env` has `*`. Check prod's `.env`, or build the link from a fixed setting (`PUBLIC_URL`).
- Web build tools only (no effect on what users download): `vite` and `source-map-js` have high-severity findings in the development server; update when convenient.

## Web: user side (browser)

- **Every page downloads 734 KB (205 KB gzip) before it renders**, up from about 625 KB (185 KB) three weeks ago. Leaflet and the map helpers (149 KB, 43 KB gzip) are in it because the Sites page imports the map directly; the stylesheet is 130 KB (22 KB gzip), one file for every page. Lazy-loading the map on Sites would take about 50 KB gzip off every first visit.
- **Session History's coverage map** (see "In short" item 3): `DtCoverageMap.tsx` draws one SVG `CircleMarker` per kept reading, each with a tooltip and handlers, up to 15,000. Fixed the same day (action item 3).
- **The site list (1.7 MB, 147 KB gzip) is fetched by every page that names sites** (Sites, Session History, others). It's cached for 60 s, so it's one fetch per page change at most. A smaller list (id, name, district, position) for the pages that only need names would roughly halve it.
- Largest lazy chunks: TRP analysis 344 KB (SheetJS), the unused style-trial page 78 KB, Subscriber Profile 75 KB. They load only when opened.
- Security in the browser: strict content policy (scripts only from the app itself, no framing, no plugins), tokens in per-tab storage, DOMPurify on every injected HTML. Gzip on the bundle and on API answers; hashed assets cached for a year, the page itself never cached.

## Mobile app

### Size
- Release APK **2.7 MB** (R8 shrink and obfuscation; debug was 9.6 MB). Nothing to do.

### Battery and memory
- **Offline queue** (`SampleQueue.kt`): every `append` reads the whole file to check the 5,000 limit, and every upload rewrites it. Keep a line count (or check every 100 appends) and trim by dropping whole old lines; better, a small SQLite table.
- Location: periodic samples every 15 min (WorkManager minimum), up to three 10-second high-accuracy fixes per sample; a drive test takes a fix every 2 s; the collector edition every 15 s indefinitely, with the battery exemption. That's expected for staff collectors, heavy for ordinary users. Keep the collector edition to staff, as decided.
- Screens poll only while visible: Signal 3 s, Cells 5 s, map redraw 2 s.
- The call queue is capped at 200, the sample queue at 5,000.

### Security
- **Good:** release is HTTPS only (cleartext only in debug builds), backup off, not debuggable, debug and info logs stripped. Only the launcher screen and Firebase's message receiver (guarded by Google's permission) are reachable by other apps; every service, receiver and provider is private. Device identity is in an encrypted store, the signing key in the Android Keystore. Uploads from registered phones are signed.
- **The shared ingest key is inside every APK.** R8 renames code but not strings, so the key is readable with standard tools. That's the reason for the two server items above (rescue enrolment, shared-key cut-off).
- No certificate pinning. With HTTPS and a public certificate that's acceptable for this stage; pinning would block interception by a user-installed certificate, at the cost of an app update whenever the certificate changes.
- `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is restricted by Google Play policy. It's fine for staff APKs installed by hand, but would need a justification or removal for Play Store distribution. `CHANGE_WIFI_STATE` is needed for the Wi-Fi scan screen.
- `DemoApplication.kt` is tracked in the mobile repo with a placeholder key (`TODO_LIVE_INGEST_KEY`; the live key was never pushed). It should be untracked so a manual `git add` can't push the real one.
