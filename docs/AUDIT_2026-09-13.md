# dtwatch Audit — Size, Memory, Performance, Efficiency, and Feature Roadmap

*Prepared 2026-09-13. Scope: the local dev deployment on your Windows machine (the sandbox bridge has no Docker socket, so a few items below could only be assessed from config/code rather than a live `docker stats`/`psql` run — flagged where that applies, with the exact command to run yourself if you want the live number).*

## Where things actually stand

Before the findings: this codebase is in noticeably better shape than a typical "audit" turns up. Most of the classic problems — N+1 queries, unpaginated hot endpoints, unindexed foreign keys, a bloated initial JS bundle, unbounded map marker rendering — have already been through at least one deliberate perf pass, and the fixes are commented in-line with dates (an August 10 backend indexing pass, an August 5 code-splitting pass, an August 7 row-limit pass, an August 15 map-marker memory pass). The findings below are what's left after that work, not a first-pass discovery of obvious problems.

One correction to how I'd been describing your setup: the *server-side* half of the crowdsourced telemetry/emergency-location work isn't waiting to be bridged from the separate Android SDK project — it's already built into dtwatch. `backend-django/core/models.py` has a full pipeline for it: `TelemetryIngestKey`, `TelemetryBatch`, `TelemetrySample`, and `TelemetryCoverageBin` for the crowdsourced-coverage side, plus `SubscriberLastLocation`, `RescueConsentPolicy`, and `RescueLocationAccessLog` for the flood-rescue beacon side, each with its own consent/audit model. There's live UI for most of it too — Telemetry Coverage, Telemetry Admin, Telemetry Live Samples, Telemetry Drive Test Sessions, Rescue Lookup, and Rescue Policy pages — and a scoped external API (`/api/external/v1/`) other systems can already read from. The Android client SDK (`netplanning-telemetry-sdk`) is still its own separate project, as expected — but the backend it should be talking to already exists here, so the telemetry/emergency suggestions below are about extending what's already in dtwatch, not designing a new bridge between two disconnected systems.

## Size and storage

The repo folder totals **1.2GB**, and more than half of that is one thing: a `samples/` directory (589MB, mostly under `samples/trp/`) that nothing in the backend actually references — it reads like raw drive-test fixture files left over from testing, not something the app depends on. Moving it out of the project folder reclaims most of the footprint immediately, with zero risk since nothing points to it.

The second-largest chunk is `data/pgdata.pre-postgis-backup/` (142MB) — a one-time safety backup taken before the PostGIS migration, deliberately kept per a comment in `docker-compose.yml`. Now that the migration has been running cleanly for a while (including the remarks/BigAutoField/attachment fixes from earlier this week), it's a reasonable candidate to archive elsewhere and delete from the working copy.

Everything else is normal: `frontend-react/node_modules` (208MB) is expected for a React + Vite + Leaflet stack, `.git` is a healthy 7.7MB, and media storage (uploaded logos, session attachments) is a negligible 332KB. There's also a stray 13MB local Python `venv/` under `backend-django/` that the Docker build doesn't use — harmless, but worth deleting or adding to `.gitignore` so it doesn't get committed by accident.

Database size, table sizes, and row counts couldn't be pulled directly (no `psql` access from this bridge) — the `pgdata` volume is 167MB on disk as a rough proxy. If you want exact numbers, run this from the project folder: `docker compose exec -T db psql -U <user> -d <db> -c "SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) FROM pg_catalog.pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 15;"`.

## Memory and resource configuration

Gunicorn itself is well-tuned: `gthread` workers sized dynamically from CPU count (capped at 12), 4 threads each, a 120-second timeout, and `max_requests`/jitter set to recycle workers periodically — all sensible for the scale this app actually runs at (dozens of concurrent users, not thousands), and Postgres's `max_connections=200` was raised to match. This is the one area where the tuning is already deliberate and documented.

What's missing is resource *limits*: none of the 8 services in `docker-compose.yml` (db, redis, django, frontend, site-sync, telemetry-maintenance, telemetry-bin-roller, and the others) have a memory or CPU cap set. In practice that means one runaway process — a large `.trp`/Excel import running synchronously in-request, for instance — has no ceiling and could starve the other containers on the same host. Adding `mem_limit` (plain Compose) or `deploy.resources.limits` per service is cheap insurance, especially for `django` and `db`.

Logging has the same "no ceiling" gap: Django and nginx both log to stdout/stderr with no file handler, which is fine, but Docker's own logging driver isn't configured with `max-size`/`max-file` in `docker-compose.yml`, so it falls back to the default unbounded `json-file` driver. This is exactly the kind of thing that looks harmless for months and then quietly fills a disk — worth adding `logging: {driver: json-file, options: {max-size: "10m", max-file: "5"}}` at the service or top level before it becomes a real problem on `ssw-prod`.

Redis is configured correctly for what it's actually used for — the shared login-lockout counter and SSO one-time codes across gunicorn workers, with AOF persistence — and isn't doing double duty as a Celery broker or channel layer (there isn't one). Its own live memory usage wasn't reachable from this bridge; `docker compose exec -T redis redis-cli info memory` will give you that if you want it, though at the current data volume (20KB on disk) it's very unlikely to be a concern.

Docker image sizes and live `docker stats` couldn't be checked either, for the same reason (no Docker socket from this sandbox). If you want those numbers: `docker images | grep dtwatch` and `docker stats --no-stream` while the stack is up.

## Backend performance

The one issue worth real attention: **Live Site Sync spawns a plain background thread inside a gunicorn worker** (`site_import.py`, the `LiveSiteSourceSyncView.post` handler) for a sync the code's own comments say can run "well past a minute." Gunicorn recycles workers periodically (by design, via `max_requests`), and there's no `graceful_timeout` override anywhere in the config, so gunicorn's default 30-second grace period can kill that worker — and the sync thread running inside it — mid-sync, silently. The client already got a "started" response, so nothing visibly fails; the sync's `last_error`/`last_success_at` fields just never update, and there's no log line pointing at what happened. This is the same class of "silent partial failure" that's already caused headaches this week with missing migrations — worth moving Live Site Sync onto the same separate-process pattern already used for `site-sync` and `telemetry-maintenance` rather than a thread inside a request-serving worker.

Second: the reporting endpoints (SLA Tracker, NTA Compliance, Monthly Report, and the KPI scatter view) each recompute a full-table Python-side aggregation on every single request, even though Redis is already configured and available as a cache backend — it's just not used for these. At today's site count this is cheap per call, but it's real duplicated work sitting on infrastructure that's already there to fix it with a short-TTL cache, invalidated when new KPI data lands.

Smaller items, roughly in order of when they'll start to matter: the Site, Drive-Test-Session, and Optimization-Activity list endpoints return unbounded results unless the caller explicitly asks for pagination — fine at current volume (thousands of sites, low hundreds of sessions), but worth a hard cap as defense-in-depth against unbounded growth. `DriveTestSession.meta` (the JSONField holding `nearby_site_ids`) is queried with a containment filter on every Site Detail page load but has no GIN index — a sequential scan today, a real cost once session counts climb into the thousands. And `Site.status`/`Site.deployment_status` are filtered in the dashboard and site list without `db_index=True` — a cheap, low-risk migration to add ahead of site-count growth. Everything else checked — N+1 queries, serializer efficiency, DB connection pooling (`CONN_MAX_AGE` is already set correctly), file storage durability — came back clean.

## Frontend performance

The highest-impact finding: on the Sites page — the default landing view after login — the map's marker-cluster rebuild effect depends on a couple of callback props (`onRelocateRequest`, `onMapClick`) that get recreated as new function references on every render of the page. Since the effect watches those props, *any* unrelated state change on that page (closing a modal, an unrelated error message, pagination) tears down and rebuilds all ~4,700 site markers from scratch, including every popup and hover listener. Wrapping those two callbacks in `useCallback` fixes it directly and is a small, contained change.

Two other map-related items, both smaller: the Explore page's per-session sample cap (15,000 points) is applied to each nearby session individually rather than to the combined total shown on the map, so a search that catches several large sessions at once can still render tens of thousands of DOM nodes. And the newest map component, the compare/delta view, doesn't yet use `preferCanvas` or a client-side cell cap the way the other three map components in this app already do — it currently relies entirely on the backend's grid-binning to keep things bounded, which is fine for short routes but untested against long or dense ones.

Live-data polling is worth a look too: both live-telemetry and live-DT-session views refetch their *entire* sample payload every 10 seconds rather than fetching only what's new — not a problem at low sample counts, but worth revisiting if live sessions start running long or tracking many devices at once.

Everything else came back clean: route-level code-splitting is used consistently, the React Query cache settings are sensibly tuned, large tables already use row-limiting and virtualization, and the session-clustering logic is correctly memoized in both places it's used (History and, as of this week, Explore).

## Suggestions for the RF / network-optimization department

Ranked roughly by usefulness against how much new work each would take, given what's already built.

**Site/sector issue tracker linked to Optimization Activity** (small–medium effort) is probably the single most useful gap to close. Right now `OptimizationActivity` models the idea of a named improvement effort with linked before/after sessions, but there's nothing representing "this is a known open problem, owned by someone, not yet tied to a fix." A lightweight ticket model — site/sector, status, assignee, optional link to the activity that eventually resolves it — reuses the exact CRUD and permission pattern already built for activities, so it's an extension of an existing pattern rather than a new subsystem.

**Multi-session "persistently poor cell" flagging** (medium effort) turns the grid-cell aggregation logic already built for the before/after delta comparison into a rolling view across *all* the sessions for a given area over time, so a cell that's shown weak RSRP/SINR across several separate drive tests gets flagged automatically instead of relying on someone noticing it by eye across separate History entries.

**Sector-level KPI trend history** (small effort) mirrors a pattern that already exists at the site level (`KpiSnapshot`, daily history) down to the sector, since sectors currently only carry their single latest KPI reading with no history — a direct copy of an established pattern, not new design.

**An interference/anomaly heuristic pass over drive-test samples** (small–medium effort) — flagging co-located high-rx_qual/low-SINR patterns or unusual PCI churn across sessions — is pure computation over data that's already collected, and could ship as a scheduled command in the same family as the existing KPI-snapshot and telemetry-bin-rolling jobs rather than a new page.

**Coloring the Sites map by congestion** (small effort) is a quick win: congestion-related KPI fields are already collected and shown as line charts per site, but there's no spatial view of them the way drive-test bands already color the map — this reuses existing map-coloring infrastructure against data that's already there.

Lower down the list: a site-detail "Issues" tab (small, but depends on the ticket tracker existing first), a scheduled report/email digest (medium — the report content already exists, but there's no outbound-email configuration anywhere in the app yet, so this needs real infrastructure, not just a template), and a dedicated field-engineer role with a touch-friendlier upload flow (small–medium, building on the role/menu-permission system that already exists). Two ideas are worth naming as *not* worth prioritizing right now: alarm/fault integration, since the codebase itself notes there's no alarm/fault data source to integrate with yet, and neighbor-list/handover suggestions, since sectors don't currently store any adjacency data and building it from scratch would be a research project, not a feature.

## Suggestions for telemetry and emergency-resilience (within dtwatch's own scope)

Given the correction above — the crowdsourced telemetry and rescue-beacon pipeline already lives in this repo — these are extensions of what's there, not a bridge to something separate.

**Exposing coverage data through the existing external API** (small effort, high value) is close to free: the API-key scoping, pagination, and rate-limiting used for the Sites and Drive-Test endpoints could cover the aggregated, already-privacy-scrubbed `TelemetryCoverageBin` data (geohash, mean signal metrics, sample/device counts) with one new scope and one new view. This is the cleanest way to make dtwatch a reliable upstream data source for anything downstream that needs coverage ground-truth — no new data collection, no new auth model.

**A coverage-confidence overlay** (small effort) on the existing Telemetry Coverage page — coloring by how fresh and dense the data behind each bin actually is, rather than only by signal strength — surfaces exactly the "where is our data too old or too sparse to trust" signal that matters for emergency planning, using data that's already being collected.

**Per-site reliability history from existing KPI snapshots** (medium effort) — surfacing which sites have historically dipped below an availability threshold most often — is a genuinely useful disaster-preparedness signal built entirely from data already in the database. Worth being explicit in the UI that this is a proxy from KPI history, not a real outage log, since there's no alarm/fault feed behind it.

**A combined drive-test-plus-telemetry density map** ("where do we actually have ground-truthed data") and a **time-boxed "incident mode" flag on a geographic area** with a simple site-status board (medium effort, but smaller than it sounds — the time-boxed, audited-override pattern already exists in the rescue-consent model and could be reused directly) round out the list. A **bulk site+sector export endpoint** (small effort) is worth doing alongside the coverage-API item if anything downstream needs a one-time full sync rather than looking up sites one at a time — right now that would take thousands of individual requests.

One idea worth flagging as something to deliberately *not* build casually: surfacing rescue-beacon device density as a general "how many people are in this area" overlay. It's tempting given the data exists, but it sits right on the consent and legal boundaries the rescue-consent model was specifically built to enforce strictly — audited, case-reference-only lookups, not an ambient dashboard layer. If that's ever wanted, it should go through the same deliberate design and confirmation the rescue lookup feature already required, not get added as a side effect of a coverage-map feature.

## If you want a starting point

Nothing here is urgent — the app is in good shape. If picking a first pass, the two things I'd fix regardless of what else you decide: the Live Site Sync background-thread issue (it can already fail silently under normal worker recycling, which is the same class of bug as this week's migration issues) and the Sites-page marker-rebuild fix (small, contained, and fixes the page every user hits first). Everything else here is worth having on a list, not worth interrupting other work for.
